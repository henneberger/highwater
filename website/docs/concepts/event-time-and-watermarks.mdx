---
title: Event time and watermarks
description: Understand progress, policy completeness, and explicit finality.
---

Event time comes from the source record. Processing time comes from the execution clock. Buffering, retries, and out-of-order arrival make them diverge.

Highwater derives watermarks from observed timestamps in `bounded` and `monotonic` modes. In `source_managed` mode, producers report progress explicitly. The combined watermark advances monotonically from the minimum across active partitions.

## Gates and lateness

`wait_until=streaming.complete` holds a Process event until the input watermark minus allowed lateness reaches the event's timestamp. Sealing every partition releases all remaining events. Waiting events consume no execution capacity.

Completeness is relative to the source and late-data policy. An inferred watermark is not proof that an older record cannot arrive. `drop` discards too-late records, `side_output` isolates them, and `accept` admits them; arbitrary Python handlers are not automatically retractable.

## Idleness and declarations

Configured idle timeouts remove quiet partitions from watermark calculation. A new event reactivates the partition, but the combined watermark cannot regress. Its historical records may therefore be too late.

Stream inspection exposes `finality.basis`: `pending`, `lateness_cutoff`, `source_declaration`, or `sealed_input`. Source declarations cover every unsealed partition, including idle ones. Sealing is irreversible. Neither source declarations nor inferred progress replace the configured late-data policy.

For business completion, a direct-ingress Process can durably finalize a quiescent key with `handle.finalize(key)`. New events are then rejected while identical retries remain idempotent. This marker is independent of event time and does not establish that outputs have reached external destinations.

## Durability

Watermarks and finalization markers persist through recovery. A completeness frontier is not a storage acknowledgement or a checkpoint coverage boundary. Journal reclamation still requires a published checkpoint covering the relevant log positions.
