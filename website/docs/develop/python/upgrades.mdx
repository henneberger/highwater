---
title: Process upgrades
description: Migrate keyed state and compare builds using captured replay inputs.
---

A Process deployment selects a build ID and state schema version. Execution records
retain their assigned build ID, and workers advertise the builds they can run.
Use a new build ID when changing application code.

## State migrations

Increasing `state_version` requires a declared migration for every intermediate
version, including changes that only add fields with defaults. Define migrations
inside the Process class:

```python
from dataclasses import dataclass
from highwater import streaming

@streaming.process(name="Balance", key="account_id", build_id="balance-v2", state_version=2)
@dataclass
class BalanceV2:
    total: int = 0
    currency: str = "USD"

    @streaming.migrate(from_version=1)
    def migrate_v1(self, state):
        return {**state, "currency": "USD"}

    @streaming.event
    async def apply(self, event):
        self.total += event.amount
        return {"total": self.total, "currency": self.currency}
```

Migrations run when a key next processes an event. The migrated state commits with
that event's successful transition. Write deterministic migrations; Highwater does
not enforce determinism. New keys start with the class defaults.

## Deploy the change

Start workers that register the new definition, then update the existing Process:

```python
handle = await client.start(BalanceV2, process_id="balances")
```

Use the existing Process ID and input configuration; for a shared input, pass the
same `source`. Keep workers for older builds available while their assigned
executions remain outstanding. Deployment updates the active build without a
worker-readiness handshake or an automatic rollout/drain controller.

The server rejects schema downgrades. Rolling back a same-schema build still
requires compatible state and handlers. Changing the Process input, workflow
name, key field, event-time field, gate, or ingress mode requires a new Process.

## Compare and save replay inputs

Retained input and reference history can be evaluated through two decorated
Process definitions before deployment:

```python
from pathlib import Path
from highwater import ReplayManifest, compare_process_builds

comparison = await client.compare_builds(
    "shopping-assistant",
    baseline=ShoppingAssistantV1,
    candidate=ShoppingAssistantV2,
)
for difference in comparison.differences:
    print(difference.event_id, difference.baseline_output, difference.candidate_output)

Path("comparison.json").write_text(comparison.manifest.to_json())
manifest = ReplayManifest.from_json(Path("comparison.json").read_text())
repeated = await compare_process_builds(
    ShoppingAssistantV1, ShoppingAssistantV2, manifest=manifest,
)
```

The manifest captures ordered records, reference histories, initial keyed state and
its version, and both build IDs and target schema versions. Its SHA-256 checksum
is verified when loaded. Reuse checks build IDs and versions and reads no live
streams. Preserve the matching code and dependencies: build IDs are labels, not
code authentication.

By default, replay starts from class defaults. To compare a selected input suffix,
call `compare_process_builds` with those records, `versioned_histories`,
`initial_states={key: state}`, and `initial_state_version`. The supplied state must
precede the first record. Each build gets an independent copy and applies its
migrations. Differences report state and output after each event.

The client captures retained input and reference histories through separate
reads; this is not a coherent snapshot across live streams. Versioned lookups use
the captured history at the original event time. Replay does not simulate
admission, watermark waiting, retries, or output delivery.

The helper writes no state or outputs to Highwater, but it executes application
code. External calls, clocks, and randomness are not recorded or intercepted;
use recorded responses or evaluation implementations for repeatable comparisons.
Store manifests with the same access controls as their captured data.
