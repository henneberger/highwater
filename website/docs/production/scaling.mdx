---
title: Scaling and backpressure
description: Scale independent keys while keeping admission bounded.
---

Highwater groups Process keys into movable partitions. A partition has one durable ownership generation at a time. The platform moves partitions and restores their state without changing Process IDs or ingestion endpoints.

## Scale out

Independent partitions run concurrently across hosts. Owners materialize state in local RocksDB and recover it from durable journals and checkpoints.

During movement, the source drains and checkpoints the partition before a higher ownership generation activates on the target. Ingestion continues through the managed endpoint and follows the new owner automatically. A delayed source cannot commit after the generation changes.

Application workers can poll selected partitions:

```bash
highwater-worker app \
  --process-only \
  --process-partitions 1,3,5,7
```

Each partition has one service owner. Application workers lease work from that owner; ownership generations fence completions from an earlier assignment.

## Calculate a replica target

`highwater-autoscaler` samples admitted work, completed work, and pending backlog. It returns a bounded replica target and a balanced partition assignment as JSON:

```bash
highwater-autoscaler \
  --process shopping-assistant \
  --target "$HIGHWATER_ADDRESS" \
  --current-replicas 4 \
  --partitions 64
```

The command can supply a decision to another scheduler. It can also watch a Process and update the Kubernetes scale subresource itself:

```bash
highwater-autoscaler \
  --process shopping-assistant \
  --target "$HIGHWATER_ADDRESS" \
  --partitions 64 \
  --watch \
  --kubernetes-deployment shopping-assistant-workers
```

Scale-down waits for the configured stabilization period and removes one replica at a time. Replica targets never exceed the number of executable partitions. The production reference in `deploy/kubernetes/hosted.yaml` grants the autoscaler access only to its worker Deployment scale resource.

## Admission-to-commit latency targets

Set a target on the Process deployment:

```python
from highwater import ProcessOptions

options = ProcessOptions(latency_target_seconds=0.5)
```

Pass these options to `client.deploy_process`. The target measures server input ingestion time to the Process transition that commits state and output. It includes mailbox waiting, completeness gates, execution, and retries; it excludes upstream source delay and delivery to an external destination. It is an operational target, not a hard completion guarantee.

The batch scheduler caps its collection deadline at the oldest eligible input's ingestion time plus the target. Once the budget is exhausted, the next worker poll can dispatch a partial batch. This does not interrupt a running invocation or bypass event-time gates, retry backoff, or per-key ordering.

`client.process(process_id)` includes a `latency` object for configured targets: oldest unfinished age, overdue unfinished count, committed mean/max latency, and committed target violations. These are diagnostics over retained outcomes, not a rolling window. Inspection scans those outcomes and becomes more expensive as history grows; use a conservative polling interval. The timestamps describe the transition recorded in the durable outcome and do not measure subsequent output delivery.

The autoscaler inherits the deployed target, or accepts `--latency-target-seconds` to override its scaling target. An override requires a Process with latency telemetry enabled. It divides unfinished work by the remaining budget and configured per-replica throughput; exhausted budgets request the configured replica ceiling. Existing traffic and backlog rules can request more capacity. Set `--min-replicas` above zero to retain warm workers; the latency target alone does not prevent scale-to-zero.

Hot keys, stalled sources, slow external calls, and worker startup can still miss the target. Replica estimates use configured throughput, so calibrate it against the workload. Targets apply to one Process; dependency-wide budget allocation is not automatic.

## Backpressure

Mailbox capacity bounds admission. When capacity is exhausted, admission fails and the producer must retry. Already accepted input remains durable while workers are inactive.

## Hot keys

One non-commutative key is sequential by design. Resolve a hot key by:

- selecting a finer key while preserving the invariant;
- using an incremental commutative aggregate;
- splitting independent state into child Processes and joining their output;
- moving expensive vector work into a size-or-latency batch.

Adding worker replicas does not create service partition owners or make a single key parallel. Configure service ownership separately and keep replica targets within the available partition count.
