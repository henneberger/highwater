---
title: Scaling and backpressure
description: Scale independent keys while keeping admission bounded.
---

Highwater groups Process keys into movable partitions. A partition has one durable ownership generation at a time. The platform moves partitions and restores their state without changing Process IDs or ingestion endpoints.

## Scale out

Independent partitions run concurrently across hosts. Hot state remains close to execution, while cold state can move to lower-cost storage and load on demand.

During movement, the source drains and checkpoints the partition before a higher ownership generation activates on the target. Ingestion continues through the managed endpoint and follows the new owner automatically. A delayed source cannot commit after the generation changes.

Application workers can poll selected partitions:

```bash
highwater-worker app \
  --process-only \
  --process-partitions 1,3,5,7
```

Each Process partition belongs to one execution instance. Durable ownership generations fence completions from an earlier assignment.

## Calculate a replica target

`highwater-autoscaler` samples admitted work, completed work, and pending backlog. It returns a bounded replica target and a balanced partition assignment as JSON:

```bash
highwater-autoscaler \
  --process shopping-assistant \
  --target "$HIGHWATER_ADDRESS" \
  --current-replicas 4 \
  --partitions 64
```

The command supplies a decision to Highwater Cloud, Kubernetes, or another scheduler. The scheduler creates the requested workers and passes each worker its assigned partitions. Scale-down waits for the configured stabilization period and removes one replica at a time. Replica targets never exceed the number of executable partitions.

## Backpressure

Capacity is communicated from execution through partition admission to producers. Highwater delays or rejects admission before a hidden queue grows without bound. SDKs retry with jitter; scheduled deployments retain already accepted input while compute is inactive.

## Hot keys

One non-commutative key is sequential by design. Resolve a hot key by:

- selecting a finer key while preserving the invariant;
- using an incremental commutative aggregate;
- splitting independent state into child Processes and joining their output;
- moving expensive vector work into a size-or-latency batch.

At 10x load, Highwater first uses available concurrency, then adds partition owners, then applies ingestion backpressure. It does not weaken fencing, skip durable commits, or advance watermarks to hide lag.
